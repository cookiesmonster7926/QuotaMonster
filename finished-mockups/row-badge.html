完成訊號 · 方向 ROW-BADGE

「現在通知跟選單列樣式可以知道需要輸入很好，但如果可以知道 session 工作完成了那就更好了。」
這個方向的賭注是：真正的問題不是通知通道，是面板本身沒有把「完成」講清楚。 所以它一個字都不動通知層，也一個 pixel 都不動選單列 —— 只重新設計 SessionRow， 讓面板一打開就能在三秒內分出這個在跑 / 這個等你 / 這個剛做完 / 這個閒著， 而且看得出剛做完的那個跑了多久、做了多少。
四個狀態用的是四個不同的感知通道，不是四個顏色： 等你＝色相（琥珀）、執行中＝動態、剛完成＝明度（整列抬起）、閒置＝缺席。 琥珀的主張是色相，抬起的主張是高度 —— 兩者在感知上不可能互相冒充， 這就是「不能用琥珀」這條限制的解法。

3 · 衰減 —— 一個不會褪色的「剛完成」就是一句永久的謊

兩個門檻都不是新常數，是把通知層已經付過代價的數字搬過來用：
90 秒 = 通知的 settle window（G2）。也就是說，如果那則通知會響，你抬頭看到的就是這個最強的狀態； 如果它被吞掉了（按 brief 自己的數字，92.6% 會被吞掉），你打開面板看到的還是同一個狀態。
10 分鐘 = 每 session 共用預算（G8，300s）的兩倍。訊號活得比整套通知機制記得這件事還久一點，然後就閉嘴。
衰減是年齡的純函式，不需要任何計時器 —— 面板開著的時候本來就每 3 秒重畫一次，面板關著的時候沒有東西要畫。 這符合這個 app「除了有東西在動的那幾秒之外，沒有重複計時器」的規則。

8 · 選了什麼 · 拒絕了什麼 · 誠實的弱點

選了什麼

  1. 訊號掛在列本身，不加卡片、不加區塊、不加區段。四個狀態用四個不同的感知通道： 等你＝色相＋呼吸、執行中＝動態、剛完成＝明度（整列抬起）、閒置＝缺席。 所以拿掉顏色還是分得開（第 2 節有灰階對照）。
  2. 完成用「抬起」當主通道、綠當副通道。 琥珀的主張是色相，抬起的主張是高度 —— 兩者在感知上不可能互相冒充。 這就是「不能用琥珀」這條限制的解法，而不是繞道。
  3. 回執寫在既有的 ctx 那一行上。 那條長條本來就佔著約 270pt 去畫一條 3pt 膠囊，縮到 42pt 就把 跑了 6m12s · 7 個 agent 整份裝進去 —— 有 statusline 讀數的 session 一個 pt 都沒加高。
  4. 綠不是新顏色。 #4CD67A = QuotaPalette.tight(onDark) srgb(0.30,0.84,0.48)，也是 SessionRow 裡 finished agent pip 已經在用的綠。 額度色階長在額度條與圖示上，完成訊號長在 session 列上，兩個表面沒有重疊。
  5. 衰減的兩個門檻都是既有常數。 90 秒 = 通知的 settle window（G2）；10 分鐘 = 每 session 共用預算（G8, 300s）的兩倍。 訊號活得比整套通知機制記得這件事還久一點，然後閉嘴。沒有發明第三套節奏。
  6. 衰減是年齡的純函式。 不需要任何計時器：面板開著本來就每 3 秒重畫， 面板關著沒有東西要畫。符合「除了有東西在動的那幾秒，沒有重複計時器」。
  7. 前 90 秒完全不變，然後一次跳到第二段。 不做連續淡出 —— 連續褪色會讓「它是不是在變」變成另一個要判讀的東西。
  8. 右邊那個時間欄位一欄兩用。 回執在的時候它是「這一輪跑了多久」， 回執走了它就換回「session 存活多久」。那一欄在 SessionRow 是 layoutPriority(3)，設計上永遠不會被擠掉，是這一列唯一保證看得到的數字。
  9. 閒置列連 ctx 長條一起壓低到 55%。 一條滿寬度的綠長條比完成訊號還搶眼，會讓「缺席」這個通道自己失效。 這是這個方向唯一動到非完成狀態的一處，寫在這裡而不是藏起來。
  10. 排序：等你 → 剛完成 → 執行中 → 閒置。 剛完成排第二而不是第一，因為只有「等你」是有時限的。
  11. 選單列一個 pixel 都不動，也不出聲。 這個方向的賭注是「問題不在通知通道」，所以它不碰通知通道 —— 它必須能單獨被證偽。

拒絕了什麼

  1. 給「完成」一個新色相。 這個 app 已經有三個顏色主張（額度藍/綠/紅、琥珀＝等你）。 第四個色相會把面板變成色票本，而且會逼近那條使用者親手釘的紅線。抬起是免費的。
  2. 面板頂端一塊「剛完成」區。 使用者已經為了高度拒絕過一張額外的卡； 而且一個會出現又消失的區段，會讓底下每一列在它出現的那一瞬間整個跳位。
  3. 右側的 NEW 藥丸。 它會撞到經過時間那一欄， 而且藥丸讀起來像一個常駐屬性，不像一個會過期的狀態 —— 與「衰減」這件事的語意相反。
  4. 把「剛完成」排到最上面（比「等你」還前面）。 等你是這個 app 裡唯一有時限的狀態。好消息不該把它擠下去。
  5. 在回執裡畫 7 顆綠 pip。 SessionRow 已經為這件事寫過註解： 「八個 10/10 的綠色 pip 沒有告訴你任何需要知道的事，只是把還在跑的那一個推出畫面。」 回執只寫一個數字。
  6. 彈簧 / 滑入 / 閃一下。 抬起用 180ms 交叉淡入，沒有位移、沒有回彈。 位移會讓底下的列跟著動，而那些列上可能正有一個你在讀的東西。
  7. 把完成也塞進選單列圖示（瞬時訊號 / 顏色 / 不透明度）。 做得到，但那會讓這個方向沒辦法被檢驗 —— 如果兩邊一起改，就不知道是哪一邊救了它。 要加也是等這一版被證明不夠之後再加。
  8. 把 T2 batchDrained 也畫成完成列。 扇出排空不等於 session 做完（協調者還要寫結論）。兩件事畫成同一個樣子， 就是把一個已知的時序差藏進視覺裡。

誠實的弱點

  1. 抬起是四個通道裡最禁不起材質的一個。 面板是 .regularMaterial，底下是使用者任意的桌布。 在亮桌布上「比鄰居亮一階」會被材質吃掉一半 —— 我押的主通道，正是 OS 有權力削弱的那一個。 補償是綠軌與勾，但那就等於在最難的情況下又退回去靠色相。第 7 節的淺色衰減格已經看得出來了。
  2. 它只在你打開面板的時候存在。 按 brief 自己的數字，92.6% 的完成不會發出通知；那些完成只有在你 10 分鐘內 剛好打開面板時才被看見。對 66% 跑不到三分鐘的 turn 大概會被看見，其餘常常會在沒人看的情況下過期。 這是刻意的，但也代表這個方向沒辦法用「使用者有沒有看到」來驗收。
  3. 「跑了多久」有兩個數字，列上只寫得下一個。 ranFor 從 unattendedSince 起算，所以 waiting → busy → idle 的 turn 會寫「你回覆後 58s」， 而使用者記得的是這一輪從頭到尾 20 分鐘。兩個都是真的。 我用換動詞去標示時鐘被重設過 —— 那是補丁，不是解法。
  4. 「做了多少」最常是空的。 一般 Agent 扇出的 agent 完成狀態在這個 repo 仍然是 .unknown （Stage 2 已知缺口），所以 7 個 agent 那一格在最想知道的時候反而寫不出來。 寫不出來就不寫 —— 但那代表回執常常只剩一個時間。
  5. ctx 長條在 70–90% 是黃色的（contextColour 現行行為）。 那是這個 app 裡唯一一個不屬於「等你」的黃色，而我把完成回執放在同一行上， 等於把這個既有的衝突擺到最顯眼的位置。第 4 節刻意畫了一個 78% 的例子把它露出來，沒有偷偷避開。
  6. 三個同時完成就失效。 抬起是相對的，三列都抬起＝沒有一列抬起（第 5 節第三格）。 這不是可以調參數調掉的，是結構性上限。
  7. 沒有「你午餐時完成了三件事」這種東西。 10 分鐘後標記就沒了，所以面板永遠說不出「你不在的時候有三件事做完」。 這個情況是被放棄的，不是被解掉的 —— 要解它需要一份歷史，而歷史需要一塊使用者還沒同意的面板高度。
